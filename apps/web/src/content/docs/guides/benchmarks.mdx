Every number here comes from a script in the repo. Run them yourself — numbers nobody can
reproduce are marketing, not measurement.

```bash
bun benchmarks/http.bench.ts       # real sockets, all five frameworks
bun benchmarks/dispatch.bench.ts   # Request -> Response, no socket
bun benchmarks/router.bench.ts     # router lookup alone
```

## HTTP throughput

Real sockets, 50 connections, `autocannon`, identical routes. Each framework runs on the
runtime it is actually deployed on.

| framework | runtime | static text req/s | param + json req/s | p99 |
| --- | --- | ---: | ---: | ---: |
| hono | bun | 114,348 | 109,920 | &lt;1 ms |
| **oven** | **bun** | **109,261** | **106,163** | **&lt;1 ms** |
| fastify | node | 84,230 | 81,171 | 1 ms |
| express | node | 18,482 | 18,339 | 5 ms |

Oven is about **5.8× Express** and **1.3× Fastify**. Hono is currently ahead of us — 3.5% on the
parameterised route, 4.7% on static text.

## Dispatch overhead

`Request` in, `Response` out, with no socket involved. Express and Fastify cannot appear here —
they are built on Node's `req`/`res` and have no `Request` entry point.

| scenario | oven | hono |
| --- | ---: | ---: |
| static root | 1664 ns | 1074 ns |
| param + json | 1931 ns | 1829 ns |
| 404 miss | 1910 ns | 1901 ns |

<Aside type="caution" title="This is not the ceiling">
  A framework that compiles each route into a specialised function at boot — with `new Function`,
  leaving no generic dispatch on the hot path — beats both of these columns comfortably. Oven
  interprets the same structure on every request. Adopting that technique is tracked as a
  post-1.0 item; doing it before the brick and context contracts settle would mean writing the
  compiler twice.
</Aside>

## Read both tables together

This is the point, and it currently runs against us.

On `static root` Hono dispatches **1.55× faster** than Oven — 590 ns of advantage. At the socket
that same pair is **4.7%** apart, not 55%. Once a real connection exists, syscalls and TCP
dominate and a few hundred nanoseconds of framework overhead compresses into near-nothing.

The dispatch table is a useful signal about where our own overhead lives, and a bad basis for
choosing a framework. We publish both, because publishing only the flattering one would be
dishonest — and publishing only the microbenchmark would mislead in the other direction.

## What none of this measures

Every framework here is fast compared to a 2 ms database query. Oven is not trying to win a
router microbenchmark; Bun makes everything fast. What we compete on is the time between
`bun create` and an app shaped like production — and no benchmark measures that.

Caveats worth knowing: loopback only, empty handlers, and the load generator shares a CPU with
the server, which compresses the top of the table. Treat anything above 100k req/s as "at the
ceiling".
