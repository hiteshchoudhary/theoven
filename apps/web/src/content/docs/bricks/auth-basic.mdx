## Install

```bash
bun add @theoven/auth @theoven/auth-basic @theoven/db @theoven/db-drizzle
```

```ts title="src/app.ts"
import { auth } from '@theoven/auth'
import { basicAuth } from '@theoven/auth-basic'

export const app = createApp()
  .use(db(drizzleSqlite({ url: './data.db', schema })))
  .use(auth(basicAuth({ db: client, secret: env.string('AUTH_SECRET') })))
```

That is the Laravel/Rails property: a working signup, login and password reset before you have
provisioned anything. SQLite is a file, and reset emails print to your terminal until you
configure a provider.

## Endpoints

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| `POST` | `/auth/signup` | create an account | none |
| `POST` | `/auth/login` | sign in | none |
| `POST` | `/auth/refresh` | new access token from the refresh cookie | cookie |
| `POST` | `/auth/logout` | revoke the session | cookie |
| `POST` | `/auth/forgot-password` | email a reset link | none |
| `POST` | `/auth/reset-password` | redeem a reset token | token |
| `POST` | `/auth/change-password` | change while signed in | bearer |
| `GET` | `/auth/me` | the current user | bearer |

The prefix is configurable: `auth(basicAuth(...), { prefix: '/identity' })`.

## What it creates

Three tables, which your migrations must include:

```ts title="src/schema.ts"
export { users, refreshTokens, resetTokens } from '@theoven/auth-basic'
```

| Table | Holds |
| --- | --- |
| `auth_users` | id, email (unique), name, argon2id hash, timestamps |
| `auth_refresh_tokens` | hashed refresh tokens, per user, with expiry |
| `auth_reset_tokens` | hashed single-use reset tokens, with expiry |

Refresh and reset tokens are stored **hashed**, so a leaked database does not hand over working
credentials. Both cascade on user delete, so removing a user cannot leave sessions that outlive
them.

## How sessions work

A **15-minute access JWT** plus a **revocable refresh token**:

```
POST /auth/login     → access JWT (body) + refresh token (httpOnly cookie)
POST /auth/refresh   → new pair; the old refresh token stops working
POST /auth/logout    → refresh row deleted
```

Identifying a request is a signature check with **no database read**. Revocation lives with the
refresh token, which is what makes logout real: delete the row and the access token expires
within its window.

The refresh token is an httpOnly cookie so a cross-site script cannot read it; the short-lived
access token goes in the body, where a client attaches it to `Authorization`.

<Aside type="note" title="Why not a plain JWT">
  "JWT" and "logout" pull against each other. A stateless token cannot be revoked, so logout
  would only clear the client's copy — the token keeps working until it expires. This is the
  design Laravel Sanctum and devise-jwt both arrived at.
</Aside>

## Configuration

| Option | Default | Purpose |
| --- | --- | --- |
| `db` | — | your Drizzle client |
| `secret` | — | **required**; signs access tokens |
| `accessTtl` | `900` | access-token seconds |
| `refreshTtl` | `2592000` | refresh-token seconds (30 days) |
| `resetTtl` | `3600` | reset-link seconds |
| `minPasswordLength` | `8` | minimum password length |
| `sendResetEmail` | — | how reset links are delivered |
| `rateLimit` | on | throttles login, signup and reset; `false` to disable |
| `refreshCookie` | `oven_refresh` | cookie name |

There is no default `secret`, and the brick refuses to construct without one. A framework that
invents a signing secret has invented a secret every deployment shares.

## Rate limiting

Login, signup and password-reset are the endpoints that actually get attacked, so they are
throttled by default. Nothing to add:

| Endpoint | Default | Keyed by |
| --- | --- | --- |
| `POST /auth/login` | 10 per 15 min | IP **and** email |
| `POST /auth/signup` | 5 per 15 min | IP |
| `POST /auth/forgot-password` | 3 per 15 min | IP **and** email |

Over the limit, the request gets `429` with a `Retry-After` header — as
[problem+json](/docs/tutorial/errors/), like every other Oven error.

Login and reset count against **both** the caller's IP and the email in the body. Either key
alone leaves a hole: limiting by IP does nothing against a distributed attempt on one account,
and limiting by email lets a single host spray the whole user table.

```ts
basicAuth({
  db: client,
  secret: env.string('AUTH_SECRET'),
  rateLimit: { login: 20, signup: 10, forgotPassword: 5, window: 5 * 60 * 1000 },
})
```

<Aside type="caution" title="The counters live in memory">
  They are per process. Behind a load balancer with four instances the effective limit is four
  times what you configured, and a deploy resets them. That is enough to blunt credential
  stuffing and reset-email spam, which is what these endpoints face — it is not a precise quota.
  If you need one, set `rateLimit: false` and put a shared-store limiter in front of `/auth/*`.
</Aside>

## Sending reset emails

```ts
basicAuth({
  db: client,
  secret: env.string('AUTH_SECRET'),
  sendResetEmail: async (to, token) => {
    await mailer.send({
      to,
      subject: 'Reset your password',
      text: `Open ${env.string('APP_URL')}/reset?token=${token}`,
    })
  },
})
```

Omit it and reset tokens are simply not delivered — the flow still works end to end in tests
and in development, where you can read the token from the store.

## Security decisions

These are the ones worth knowing about, because they shape what the endpoints return:

- **Login does not reveal which emails exist.** A wrong password and an unknown address get an
  identical body, an identical status, and comparable timing — an unknown email still pays an
  argon2 verification against a decoy hash.
- **Forgot-password always succeeds.** Reporting "no such account" would make it an enumeration
  endpoint. The person who owns the address finds out by email.
- **Refresh tokens rotate.** Using one invalidates it. A refresh token that survives its own use
  is one a thief keeps using alongside the real client.
- **Reset tokens are single-use and expiring**, and redeeming one signs every session out.
- **Changing a password signs every other session out.** Someone changing a password usually
  believes an account is compromised.

Each of these has a test, including the enumeration and token-reuse cases.

## Where the code lives

Almost none of this package is in this package. The flows, the eight endpoints, the cookie
handling, the rate limits and every piece of cryptography live in `@theoven/auth`, shared with
[`auth-mongo`](/docs/bricks/auth-mongo/) and any other storage brick. What is here is
`schema.ts` and `store.ts` — the Drizzle half, and nothing security-critical.

That split is the reason `auth-mongo` is a hundred lines rather than a fork. Two auth bricks with
their own copies of the token logic is a fix landing in one and not the other, which is the bug
nobody finds.

## Limitations

- **SQLite schema only.** The tables are declared with `drizzle-orm/sqlite-core`. Postgres works
  as a database, but you would restate the schema with `pg-core` today.
- **No email verification.** `auth_users.email_verified_at` exists and is never set.
- **Rate limiting is per process**, not shared across instances — see the caveat
  [above](#rate-limiting).
- **No OAuth.** Use [`auth-clerk`](/docs/bricks/auth-clerk/) or [`auth-better`](/docs/bricks/auth-better/) — both ship, and both satisfy the same contract,
  so `auth: true` and your policies keep working.
